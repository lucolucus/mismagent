# 0.7.27 plan — specify beside the build

The human asked to work in parallel (2026-11-06): while `/loop /mismagent:build` builds release R,
add examples and slices to R from another session. The README's answer so far was "work in another
checkout, or it waits while the tree is dirty". In one checkout, two things broke the parallel
work: the specify interview left its files uncommitted until its close, so the loop waited for the
whole interview (ten minutes a tick); and two hands committing with `git add -A` sweep each
other's files — a builder commit that carries an example is refused by `check --base` (not the
human's), a specify commit that carries code is not the human's either, and either way the gate
goes red for the wrong person. Specify was also written for "the next release": adding a
capability to the one being built was nowhere said (a bug already went there, §6).

## Changes

- **`mm spec "<note>"`** (`mm.py`): the human's commit beside a build. The spec paths only —
  brief, event storm, releases, examples, slices in todo, decisions, artboards, stack reviews —
  with the subject `specify <note>` that `check --base` reads as the human's. It refuses a spec
  that does not hold together (every `mm check` error under `.mismagent/`, whichever file it
  names), a rename across the spec paths, a path staged with other content than the tree's;
  paths as committed already: no commit, the index reconciled. `git status -z`: a quoted name is
  read as it is.
- **One way to commit, `publish`**, for every commit mm makes (`spec`, `start`, `park`, `built`,
  `land`, the release review at `tag`): the tree's state of the named paths, built in an index of
  its own (`GIT_INDEX_FILE`), set on HEAD with `update-ref <new> <expected>` — HEAD moved since
  the preconditions were checked: refused, the files put back, run again (`spec` selects, checks
  and builds again, three times). The shared index is never staged, so a builder's commit beside
  mm carries nothing of mm's; afterwards the shared index follows HEAD on those paths alone. A tag
  names the commit it was checked on.
- **One lock** (`.git/mismagent.lock`, an OS lock held for the process's life: a crash releases
  it, a reused pid means nothing) around mm's state moves and `spec`, taken before the state is
  read, so what was checked is what moves; waited for 30 s (`$MM_LOCK_WAIT`). **One HEAD** is read
  under the lock, checked and used as the commit's parent: never one for the check and another
  for the parent. **`land` and `tag` check their preconditions again after the gate**, which
  takes a while and holds no lock: a slice or an example that joined the release meanwhile holds
  the tag; a code commit during the gate voids the PASS. A refused publish puts the slice file
  back byte for byte; published but the index could not follow (an `index.lock` beside mm past
  ten tries): the commit stands, said as such, nothing put back. The review files are committed
  one by one, so a draft is never in a commit, and drafts go only once the commit stands.
- **A specify commit changes no code**, nor does the `review: <release>` commit `tag` makes of the
  review's own files, so a review at the commit below either is still at HEAD: `code_heads` walks
  down through single-parent commits whose diff from the parent (renames undone, so moved code
  shows) touches those paths alone — a merge never — and `land`, `tag`, `built`, `review` and
  `next` read through them. A spec commit no longer invalidates a review nor sends the builder
  back as "cut before `mm built`"; a `tag` cut after its review commit finishes at the next run.
- **`wait`**: `mm next` says it when the tree is dirty with spec paths alone (specify is writing,
  with the files and the minutes since its last write); `start`, `built`, `land`, `review`, `tag`
  and the gate's base check name specify's files when they refuse, so no agent "fixes" the
  human's file by committing it. The conductor comes back in two minutes; past half an hour it
  tells the human once.
- **`skills/specify`**: a section *Beside the build*, holding on every route (intake, stack
  review, bug) — commit each file as it is written with `MM spec`, never by hand (a doing slice's
  `## Answer` alone is committed by hand, that file only); whole files, examples before the slice
  that names them, the window short (the tree is shared: a half-written file is on the builder's
  disk the moment it is written, and `mm` holds the flow until it is committed); the release in
  hand (the doing slice's, else the first untagged in order, or the one the human names — §6's
  fix slice goes there too); a slice added starts in its turn; a release under review goes back
  to the build; an example a started slice names is superseded, never rewritten. §4 proposes the
  slices and gets the release cut **before** writing them: a file in `todo/` is runnable the
  moment it is committed. §5 closes on the spec's own errors (a red line on code is the builder's)
  and `MM spec`.
- **`commands/build.md`**: the `wait` action; a refusal that names specify, a moved HEAD, the lock
  or a precondition that moved under it is a wait and `MM next` again, not a `NEEDS-HUMAN`; its
  own `## Answer` committed by path.
- **`agents/mismagent-builder.md`**: stage by path, never `-A`, `.` or `-a`; `mm built` refused
  for specify's dirt → wait, never commit or touch those files. **`mismagent-architect.md`**: the
  stack review's files go through `MM spec`.
- **`hooks/guard-git.py`** backs that rule for the three agents: `git add -A`/`--all`/`-u`/`.`/`:/`,
  `commit -a`, `clean` and `restore` are denied beside `stash` and `checkout` — the human's
  uncommitted example is an untracked file a `clean -fd` deletes without a trace, and a `restore`
  reverts their edit; the hook reads the literal command, so it backs the prompt, not replaces it.

## Not done
Parallel building stays out (hypothesis K7: slices in sequence, one integrator). Git has one
index per checkout and no transaction across commands, so a *raw* git commit by the builder (its
own, outside mm) in the milliseconds between mm's `update-ref` and its `git reset -- <paths>`
reverts the spec paths in that commit: the human's file is still on disk, the next `mm spec`
commits it again, and the excursion cancels in `check --base` — a nuisance, never a stuck gate.
A builder's own `git commit -a` or `git add -A` of the human's uncommitted file (the prompt
forbids it, the hook denies the literal command, an indirection slips past) leaves a commit
`check --base` refuses: the human puts the file back as at Base in a commit of its own and `spec`s
it again. Two sessions editing the same file in the same minute —
the conductor's open-question line in a release file specify is writing — is not guarded: the
later write wins, and an edit never committed leaves no trace in git. A staged version of a
spec path put there by someone else between `spec`'s check and its reconciliation is replaced
(nobody stages spec paths but `spec`); `code_heads` stops after 200 specify commits in a row.
The tests prove the mechanisms one at a time and the schedules a git on PATH can inject (a
commit beside mm, a reconciliation that fails); they do not pause mm mid-command.

## What should move
- The conductor's waits on a dirty tree during an interview: from the interview's length to a
  two-minute tick.
- `mm built` refusals "changed since … not the human's" while specify runs beside: 0.
- Reviews redone, slices resumed, because of a spec commit: 0.
- `mm log`: no `tool` or `spec` line about waiting for the loop, or committing beside it.
