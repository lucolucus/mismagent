# 0.7.26 plan — what an external review of a built app traced back to the method

An external architecture review of Wiki Around (iOS, ~10k lines of Swift, built with 0.7.x) was
verified by a second model (gpt-6-astra, read-only), then the harness changes were cross-checked by
claude-fable-5-1 and triaged by gpt-6-astra against this code (2026-11-04). Only the findings the
method caused or could have prevented are acted on here.

## What the review found, and the method's part

| finding (verified) | the method's part |
|---|---|
| `.mismagent/` 151 MB, 136 MB of shot PNGs | `mm built` committed a set of screens every round (`git add … *shots`); `mm tag` a release's |
| `ARCHITECTURE.md` 45 KB, a slice-by-slice chronicle with `file:line` refs, one line stale after slice 81 | the template put a **Change log** in the map; the "file and line" evidence rule was applied to a living document; only the design pass updated the map; no sensor on it |
| the smoke builds search without languages: it proves another app | `smoke:` said "starts the app, exercises one use case" — never "from the app's composition root" |
| shot scenario branches threaded through production views | `shot:` said what to render, not from where; the builder wrote it mid-slice |
| 13 use cases with a `static let assente` default in a production init: a forgotten one compiles and vanishes | the composition-root topic existed as a slot, with no rule |
| Domain folders by concept and by type; mixed IT/EN names | the map had no packaging criterion nor a language of names |

Not acted on: the write-through copy (a design judgment, the review withdrew its decorator);
adapters built twice in the root (cheap); `CopieAssenti` (no direction broken); Application as
ceremony (a pass-through use case per example follows from "one thing per file" + acceptance at the
use-case seam — the human's decision, deferred); a fast gate (unmeasured: measured first, below).

## Changes

- **A. Shots** (`mm.py`). `mm built` renders a slice's screens to disk and no longer commits them;
  `mm tag` commits the release's set with `git add -f` (past a `.gitignore`, which the skeleton now
  writes for `.mismagent/shots/`). `mm check` warns once on slice shot sets still tracked, with the
  `git rm -r --cached` command; the history keeps them until rewritten (the project's call). Not
  assumed: that shots are reproducible (`shoot` checks presence, not determinism) — so the release's
  set is still committed.
- **B. The map.** Architect: the map is the code as it is now, by paths and symbols; no change log
  (a changed decision is a decision file with `supersedes:`; the conventions skill writes its
  changed rules there too); line numbers are evidence only in what is read at one commit; a
  packaging criterion and the language of names. Builder: a slice that changes what the map says
  updates it. Reviewer: a map line the diff made false, or a map warning the diff caused, is
  blocking. `mm check` warns (not errors: the skeleton maps code to come) on a cited path no file
  has, on a `file:line`, on more than `max_map_lines` (300) lines.
- **C. Smoke**: built from the composition root the app starts from, with its real configuration,
  only the external replaced and named; the release reviewer names the root it built from, and a
  smoke assembled apart is a Modularity finding.
- **D. Shot harness**: drives the app from outside the production views (a scenarios target or
  wrapper, or the UI test driver); a tests kind in the first conventions; builder Never, review
  table row.
- **E. Composition root**: the skeleton's proposal for that topic carries "every functional
  dependency a required parameter of a production initializer; sub-states built in the root; fakes
  in test factories" — the human decides it in `/mismagent:conventions`.
- **F. Gate seconds**: the gate prints each command's seconds and its total; `mm built` writes
  `Gate: <round>: <seconds>`; `mm log` reports median, p75, max.

## What should move

- `.mismagent/` growth per slice with `Design:`: from one PNG set per round to zero.
- Map: no `file:line`, no stale path at a release review; the map's size stops growing with slices.
- Release reviews: a smoke that is not the app's, a scenario branch in a view, a defaulted use case
  — each found in the review that follows the slice, not by an outside reviewer.
