# v0.25.0 plan — the composer diet

## Evidence (run 6, RegistratoreCassa6, v0.24, Sonnet)

Build tokens 132M: the composer's main session **96.5M (73%)**, workers 24.5M, verifier 7.7M,
code-review 3.1M. The runner resumed ONE composer session across 9 firings (fixed in v0.24's
`bench/run.py`: fresh session per firing). Within the composer's context, what it added
(344 tool calls, 469k chars of tool results):

| source | share | detail |
|---|---|---|
| subagent returns (`Agent`) | **50%** | 51 returns; worker avg 4.1k chars, verifier 5.6k (max 8.1k), code-review 4.9k — the "tight return" is not tight |
| whole-file reads | **17%** | `cat tools/CLI.md` (32 KB) and `cat building-blocks.yaml` (43 KB), persisted then re-read |
| per-block ceremony | the rest | ~20 tool calls per block: diff-range, compose start/promote, gate, move, proof record, ready, status, **32 `git add`/commit of bookkeeping** (also friction #2: uncommitted housekeeping collides with a worker) |

Every token that enters the composer's context is re-read on every later turn of that session:
shrinking what enters it is the lever (fresh sessions only reset the growth per firing).

## Changes

### 1 — Reviews go to a file; the composer gets a verdict line
- `mismagent-verifier` and `code-review` write their full result (checks, findings with file:line,
  evidence) to **`F/reviews/<id>-<n>.json`** — their ONLY write, a file no one else writes — and
  return ≤ 5 lines: `VERDICT`, `HEAD_SHA`, counts by severity, the file path.
- **`MM review ingest F <id> --file F/reviews/<id>-<n>.json --sha <head>`** (the composer runs it):
  validates the JSON, appends every MED/LOW line to `pre-release.md` (single writer = the tool, run
  by the composer), writes the rework file for HIGHs (`F/rework/<id>-<n>.md`), records the review
  proof when clean; outputs a one-line summary. The composer never reads the findings.
- guard hook: verifier/code-review may write under `F/reviews/` only.

### 2 — The worker's return is capped
- Worker `DECISIONS`/`DEVIATIONS`/`NOTE` stay, but the full decision-note entries go to a committed
  file in its worktree (`.mismagent-return/<id>.md`, removed by the composer after `why append`
  ingests it) — or simpler: **`MM why append … --from <worktree>`** reads them from the block
  branch. The Agent return is ≤ 8 lines. (Choose the simpler after checking `why append`.)

### 3 — No whole-file reads by the composer
- `MM help <command>` prints one command's usage + semantics (from CLI.md sections); the composer
  prompt says: never read CLI.md, LOOP.md or the manifest whole — ask the tool (`ready`, `status`,
  `pack`, `help`). Every JSON output the composer consumes stays ≤ ~2 KB by default (`--full` for
  the rest); check `status`/`ready`/`lint` sizes on a 34-block manifest.

### 4 — The tool commits its own bookkeeping
- Every tool command that writes state on the integration line (`move`, `proof record`,
  `progress record`, `review ingest`, `release *`) commits exactly the files it wrote, with a
  generated message, unless `--no-commit`. Removes the composer's `git add`/commit turns and
  friction #2 (housekeeping never left uncommitted). Refuse when unrelated staged changes exist.

### 5 — Bounded firing
- The composer ends a firing after **N integrations** (profile `build.integrations_per_firing`,
  default 4) with its report; `/loop` or `bench/run.py` starts a fresh one (state is on disk).
  Bounds the within-firing growth the fresh-session runner cannot.

## Rev. 2 — after Codex's verification (2 HIGH, 3 MED): simpler variants, build order 3 → 2 → 1 → 5 → 4

- **3 (minimal, best ratio):** the composer never reads CLI.md, LOOP.md or the manifest whole; it
  asks `MM <command> --help` (argparse descriptions gain one-line semantics) and the JSON commands.
  Packs are saved to files and passed by path. No universal 2 KB cap (a 34-block `ready` is 3.5 KB);
  summarize only verbose lists, never hide anomalies, `bounce_to`, finishable or resume items.
- **2 (durable handoffs):** the composer designates, per dispatch, an ignored absolute path
  `.worktrees/returns/<feature>/<id>-<attempt>.md`; the worker writes its decision-note entries
  there (no committed file, no new `why --from`), returns ≤ 8 short lines (RESULT, counts, contract
  deviations, BLOCKED/BOUNCED cause, checkpoint pointer, the handoff path). After promotion the
  composer runs the existing `MM why append --entry <file>`; entries from every attempt are kept.
- **1 (review reports):** the composer designates
  `.worktrees/reviews/<feature>/<id>-<attempt>-<verifier|code-review>.json` (absolute, ignored);
  the reviewer writes its full report there (`{version,id,attempt,reviewer,sha,spec_hash,verdict,
  checks,failures,findings:[{sev,at,issue,fix,evidence}],notes}`) and returns ≤ 5 lines.
  **`MM review ingest F <id> --attempt N --depth standard|deep --file <report>… --sha S
  --spec-hash H`**: requires the full reviewer set for the depth (standard: verifier; deep: verifier
  + code-review), same block/sha/reviewed spec hash; appends MED/LOW to `pre-release.md` idempotently
  (existing 7-field lines, finding identity), writes ONE `rework/<id>-<n>.md` per failed cycle
  (keeps the 2-cycle cap), records the review proof only when every report passes; returns
  `{action: promote|rework|park|decide, reason, rework, counts}`. The verifier gains `Write` for
  that one file (prose-enforced; the hook cannot confine Write).
- **5 (bounded firing):** one completed dispatch wave per firing — every dispatched block
  integrated, parked or blocked, no candidate open — then report and end; the next firing is fresh.
- **4 (optional helper):** `MM state commit F -m <msg>`: on the integration checkout only (branch
  check), stages exactly the changed/deleted tracked-or-new paths under `<output_dir>`, refuses other
  staged changes; the composer calls it before `compose start` and after `compose promote`, never
  between. No implicit commits in other commands.
- Measure against a **fresh-session v0.24 baseline** (the current resume of run 6), not run 6's
  resumed-session number.
