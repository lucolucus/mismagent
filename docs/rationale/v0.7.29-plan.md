# 0.7.29 plan — two costs measured on the projects built with the method

The human asked for an honest review of the method (2026-11-10), checked by a second model
(gpt-6-astra, on a copy). Beside what both said of the evidence — the long-horizon experiment
never run, fifteen core hypotheses neither confirmed nor refuted — the review measured where the
time and the tokens go in the projects already built with 0.7.x. Two numbers, one change each.

## What was measured

**The gate, three times a round.** `mm built` runs the gate, the reviewer runs `mm gate --base`,
`mm land` runs it again — on the same code: between the three only `.mismagent/` moves (the
card's headers, the review, the move to done). wiki_planet, `mm log`: gate median 831 s (9 rounds
on record, p75 841 s, max 1806 s); its landed slices take a median 40 minutes of wall-clock — three
gates. A release adds two (its review, `tag`). The 0.7.28 plan left it open: "the gate runs three
times a round".

**The conductor reads more than the builders.** `bench/cost.py` on the transcripts of four
projects (`~/.claude/projects/…`, 2026-11-10), tokens of every class:

| project | all | main sessions | builders | reviewers | architect |
|---|---|---|---|---|---|
| wiki_planet | 1,219 M | 747 M (61%) | 388 M | 48 M | 35 M |
| meterbb | 944 M | 607 M (64%) | 221 M | 49 M | 23 M |
| dss-rust | 363 M | 276 M (76%) | 72 M | 13 M | 3 M |
| p7read | 1,559 M | 796 M (51%) | 636 M | 55 M | 36 M |

Nearly all of it is cache read: fewer dollars than tokens, not converted here (no price list
taken). "Main" is every session a human opened in the project: the conductor's, and specify or
conventions when they ran in the same conversation (p7read: 615 M in sessions that ran the
conductor alone). Those sessions ran on `claude-opus-5-5` with a 1M window, and their context
grows with every tick and is never cut: in the seven largest sessions of wiki_planet and p7read,
median 162–541 k tokens a call, up to 920 k. One of them
(wiki_planet, 769 calls, 250 M tokens): 143 `mm next`, 82 dispatches, 6 lands — 5.4 calls a tick,
each reading the whole conversation. What fills it, in characters: the `/loop` skill's own text,
appended again at each of its 70 firings (573 k); messages from another session (288 k); the
conductor's tool calls (309 k) and words (171 k); tool results (about 410 k). No single thing to
trim: the conversation has to be cut. The rule that should have cut it — `/clear` after the third
`land` — counts lands, and the context grows by tick: 143 ticks for 6 lands.

## Changes

- **A. The suite runs once per code tree** (`mm.py`: `code_tree`, `on_disk`, `gating`, `gated`,
  `record_gate`, `gate`). A green `test` or `lint` goes on record in `.git/mismagent.gate/` under
  the hash of HEAD's tree without `.mismagent/` — the command, its seconds, when, and what the
  tracked files were on disk (each name as written, its type, mode, size, links, the times of its
  last write and of its last change of any kind, its directories' modes and flags, in one hash) — with the whole output of that run beside it. A gate with the same command prints
  that run and the output's path and does not run it again **only while running it would read the
  same files**: the same commit's code, nothing uncommitted outside `.mismagent/` (untracked
  debris too, a file moved into `.mismagent/` too: the line says which file), and every tracked
  file on disk as that run left it. `check` always runs again (it is cheap, and it is what reads
  `.mismagent/`). Nothing goes on record from a tree with a submodule, from a red run, or from a
  command that touched a tracked file (the command after it runs as well: the tree is read
  before each). A run that starts drops what was on record for its command, and one gate's
  commands run at a time in a checkout (`.git/mismagent.gate.lock`; a second gate waits, as long
  as two commands may take, then finds the first's run): a run red, cut or timed out is followed
  by a real one, never by a green still running beside it. `mm gate --fresh` runs what is on
  record. The five newest trees are kept, the output of a red one too, pruned after every run; a
  dirty tree's output is one file a command; an output file opens with the line of its run
  (command, verdict, seconds, time) and is moved in whole, since a later run on the same tree
  writes the same file. Without a file lock (Windows) nothing is on record: the suite runs as
  before. `Gate: <round>: <seconds>` counts the seconds of a run not repeated, so `mm log` still
  reports what a full gate costs.
- **What the record promises** is what the run it stands for promised: the suite green on this
  checkout — not on a clone. 0.7.28 ran the suite on the disk three times and never said more.
  The one question a record must answer is whether a run now would read other files than the run
  then; `git status` does not answer it (below, rounds three to six), so `mm` looks at the disk.
- **The output is kept, green too.** The gate printed the last fifteen lines of a red command and
  nothing of a green one, while the reviewer is asked to prove each acceptance test *ran*:
  wiki_planet's friction log has it three times ("gate output names no test; read the xcresult").
  Every run's output is now a file the gate names.
- **Prompts.** Reviewer, slice: the gate names the run and its output — the evidence that a test
  ran is read there; `--fresh` for a suite it has a reason to doubt. Reviewer, release: `mm gate
  --fresh` — one real run of the suite per release, by fresh eyes; `tag` then reads it. Builder:
  the last full run is `mm gate --base` on the committed tree, and `mm built` does not repeat it.
- **B. The conductor's session is compacted.** No code: Claude Code has the window
  (`claude --autocompact 100k`, 100k–1M; 2.1.322), and `/loop` has no way to start a tick from an
  empty context (its documentation, *scheduled tasks*: a firing runs between the turns of one
  session; nothing documented clears a session from inside). The READMEs say to start the loop's session with it. The state is in the repo, as
  `build.md` already says.

## What should move

- Suite runs per single-round slice: 3 → 1; per release of N such slices: 3N + 2 → N + 1. On
  wiki_planet, wall-clock per landed slice (`mm log`): median 40 min → about a third, if the gate
  is what fills it. Read at its next release.
- Friction `tool: gate output names no test` (three reviews in wiki_planet's log) → 0.
- Main sessions' share of a project's tokens (`bench/cost.py`, the table above): 51–76% → under a
  third; the conductor's context a call: median 162–541 k → under 100 k. An estimate until a
  release is built with the flag: a window of 100 k over 5.4 calls a tick is about a quarter of
  what was read.

## Not done

- **The record is not signed.** It lives in `.git/`, out of every commit and of the tree an agent
  edits; an agent that wrote there by hand would forge a green, as one that typed `Built:` would.
  What bounds it is the release review's fresh run. No hook added for it.
- **What the hash does not see**: a test that reads `.mismagent/`; an ignored file, a simulator,
  the network, the date. Such a suite is run with `--fresh`, by the reviewer who doubts it. A
  linter that reads `.mismagent/` (a Markdown lint over the whole tree) is in the same case.
- **A tracked file rewritten with its size and both its times kept** — during the suite or
  between two gates — is not seen: the disk is read by name, type, mode, size, links and times,
  not by content (the content of a tree with large assets costs seconds a gate, four times a
  gate). It takes a writer that sets a file's times back, or a filesystem that keeps whole
  seconds (HFS+; APFS keeps nanoseconds: 100,000 writes of one size, no two times alike) and two
  writes within one. A directory's ACL is not read either (its mode is; its times move with every
  temporary file a suite writes there). Code is written in the checkout by the builder alone;
  `--fresh` for the suite one doubts.
- **A change to what the hash holds that writes no byte takes the record with it**: an extended
  attribute macOS sets on a file (quarantine, last-used date), a flag, an identical save from an
  editor move the file's time of last change, and the next gate runs. No regression — the suite runs as it did — and no gain
  for that round. From `built` to `land` nothing in the method does it (round eight, measured);
  how often a desktop application does is not measured.
- **What the hash leaves out**: a file's access time, and of a directory everything but its
  spelling, type, mode and flags — its times, its group, its extended attributes, its ACL. A
  suite whose verdict hangs on one of those (reproduced in round nine only with suites that
  assert the metadata itself, and with a directory ACL that denies a write) wants `--fresh`.
- **The output a gate names is the last run's, not an archive**: a later run on the same tree
  writes the same path, and the tree leaves with the sixth after it. A review quotes what it read.
- **A gate killed leaves its suite running** (the lock goes with the process, the suite's own
  group does not): the next gate may run beside that orphan. It cannot write the record; two
  suites may still meet on a simulator. `mm` ends the group when it is interrupted, not when it
  is killed.
- **The look costs.** Twice a gate that reads the record, four times one that runs: on about
  10,000 tracked files, 0.1 s each in 100 directories, 0.3 s in 10,000 — a reused gate 0.5 to
  1.5 s where 0.7.28's took 0.2 s before its suite.
- **A suite that touches a tracked file every time** (a generated project written again with the
  same bytes, a formatter in `lint:` that rewrites what it did not change) keeps itself off the
  record, and the command before it too; the gate says so: it runs as before 0.7.29.
- **A project that leaves untracked files outside `.mismagent/` after its suite** (no
  `.gitignore` for its caches) gets no record, and the gate says which file each time: the
  suite runs as before 0.7.29 until the file is ignored. The four projects measured are clean.
- **`/clear` after the third land stays in `build.md`.** With the window set it is a stop the
  human no longer needs; without it, it is the only cut there is. Dropping it, or counting ticks,
  waits for a release built with the flag.
- **A runner that fires each action in a session of its own** (`bench/build_loop.py`, made a
  tool): no token while the flow waits for the human, and by the same estimate about half of what
  the compacted session would read. It changes how the human talks to the conductor and needs the permissions a
  headless session cannot ask for: decided only if the share above stays high.
- **Waiting costs.** A tick that finds the flow waiting for the human still reads the session:
  about a third of the ticks in the session above. Unchanged.

## Tests (`tools/tests/test_mm.py`, class `Gate`)
A second gate on a clean tree does not run the command and names the run and its whole output
(forty lines, not the tail); a commit under `.mismagent/` alone keeps the record, a commit of code
does not; `--fresh` runs it; nothing on record from a dirty tree, a red run, a command that
changed the code (and the command after it runs), untracked debris, a submodule, a file moved
into `.mismagent/`; a red `--fresh` is followed by a real run; two names a carriage return apart
are two trees; five gates at once run one at a time (a suite that fails when two overlap), and
five plain ones run it once; a gate does not wait past its time for another; a file a sparse checkout took away, one edited under assume-unchanged, a mode bit under
`core.filemode=false` (the owner's alone too), a name respelt by case or by composition where git
folds both, a directory closed to writing or respelt, a link retargeted to the same file, a hard
link added, a size changed with the time set back, a time a microsecond off, a file touched or
written again by a checkout: each is a run, and the same disk twice is not; trees wholly red leave with the others; a
record of another shape, or one that lost its output, is a run;
built, reviewed and landed run the suite once; `Gate:` counts the seconds of the run not
repeated; the five newest trees kept, by name, red and dirty output bounded with them. `test_land_checks_again_after_the_gate` forgets the record first: it pins a commit made
during a gate that runs.

## Reviewed by Codex (gpt-6-astra, 2026-11-10), on a copy

**Round one** (the first cut: the tree listed as text, one record file per tree, the output under
a fixed name, run debris let through as in `clean`): rework, six findings reproduced in scratch
repositories, one on the tests. Taken:
- `git ls-tree` read as text turned a carriage return into a newline: `input\rdata` renamed
  `input\ndata` kept the same hash, and `built` and `tag` passed on the other tree's green. The
  listing is hashed as bytes.
- A red `--fresh` left the old green on record and wrote its failing output over the green one:
  `tag` then passed on the record, naming a failure as its evidence. A run that starts drops the
  record; each run's output is a file of its own, named by its record.
- `DEBRIS` (`\.sqlite[^/]*$`) took an untracked `src/broken.sqlite.py` for run debris: the record
  stood over a source file the suite would have compiled. No exception: anything uncommitted
  outside `.mismagent/` keeps the run off the record.
- A deinitialized submodule left the gitlink, and so the hash, unchanged with its files gone: a
  tree with a gitlink is never on record.
- Twelve gates at once shared `<tree>.json.tmp` and one crashed on `os.replace`: a record per
  command, written from a temporary file of its own.
- Two mutations survived (the oldest trees kept, the output cut to its tail): the tests name the
  trees kept and read forty lines.

Accepted as a boundary (above): a file edited and put back while the suite runs.

What held: the run counts (one slice and its release 5 → 2; with a rework 7 → 3; with a design
pass and a second release review 6 → 3), nested `.mismagent/`, symlinks, tabs and newlines in
paths, a detached HEAD, a linked worktree, a repository with no commit.

**Round two** (the listing as bytes, a record a command, an output file a run, `forget` before a
run): rework again — of the six, four closed, one accepted, two in part, and seven findings on
the new code. Taken:
- `git mv src/cart.py .mismagent/reviews/` staged: `status` gives a rename's two names and
  `code_tree` read the new one only — the tree passed for clean, and `land` on the record with the
  source gone. Both names count.
- `test` green but writing the code: its own run stayed off the record, and `lint`, looked up
  under the tree read before the loop, was taken from the record — `built` passed over code a
  lint run turns red. The tree is read before each command.
- A green run still going when a `--fresh` beside it dropped the record, then finishing first:
  its green was back on record after the red, and `tag` passed. And `forget` deleted the other
  run's temporary file (a crash on `os.replace`) and the output a third gate had just named.
  One answer to the three: a lock a checkout, held from the look at the record to its writing;
  with it the output is again one file a tree and a command, and `forget` is one `remove`.
- The output of dirty runs and of trees wholly red was never pruned (pruning read the records
  only): bounded as above.
- A record of valid JSON and another shape (`seconds` missing, `at` a list) raised on reuse: no
  record.
- Mutations that survived (one output name for every run, the check that the output is still
  there): the lock made the first moot; the second is pinned, with the lock itself.

The boundary of round one — a file edited and put back while the suite runs — Codex found to
hold for the writers the method allows (specify's paths are under `.mismagent/`, the conductor
and the reviewer edit no code, `mm` writes none).

**Round three** (the lock, the tree read before each command, one output file a tree and a
command): rework — of the seven, four closed and three in part, four findings. Taken:
- `git sparse-checkout set '/*' '!/src/'` takes the source off the disk and leaves `git status`
  empty: `built` passed on the record. So did a file edited under `--assume-unchanged` or
  `--skip-worktree`. A checkout where `git ls-files -v` shows any entry not plainly cached is
  never on record.
- A tree whose two commands were both red never reached the pruning, which ran on a record's
  writing: it runs after every gate's commands.
- The wait for another gate had no end (an owner stopped, not dead): it lasts as long as two
  commands may take, then refuses.
- An output file handed to a reader is written again by a later run on the same tree (a red
  `--fresh` after the green): each file now opens with the line of its run, so what is read says
  which run it was. Kept as one file a tree and a command: a file a run asks for a second
  retention rule, and the review quotes what it read.

What held: no inversion between the gate's lock and `mm`'s own (`built`, `land` and `tag` leave
the first before taking the second), a killed owner frees the lock and cannot publish late,
linked worktrees each with their record.

**Round four** (the check on files git does not look at, pruning after every run, the bounded
wait, the first line of an output file): rework — of the four, three closed, one in part, three
findings. Taken:
- An output file was rewritten in place: a reader holding it open across a later run could read
  the green's first line over the red's body. It is written whole beside and moved in.
- The test of the first line read its format only (a wrong command, a fixed date, `green` over a
  red run all passed): it compares the line with what the gate printed, bounds its time, and
  reads the same file red after a red run.

A rename by case alone on a case-folding filesystem and a mode bit under `core.filemode=false`
(`status` empty, the index entry plainly cached, a suite red on that disk) were first argued as a
boundary: the record is the commit's, and a clone passes.

What held: split index, untracked cache and fsmonitor leave the record on; an intent-to-add and
an unresolved merge take it off through `status`; a refusal on the lock leaves HEAD, the index,
the tags and the cards as they were under `built`, `land` and `tag`.

**Round five** (the output moved in whole, the first line's test, the boundary argued): rework —
the two closed, and the boundary refuted by turning it round. With the difference on disk
*before* the first gate — `src/CART.py` committed and renamed `cart.py`, or a 100644 file made
executable under `core.filemode=false` — the suite is green on the disk and red on a clone of
that same HEAD; the record kept the green after the disk was put back, and `land` and `tag`
passed on it. The record was not the commit's. Taken: where git is set not to see them
(`core.ignorecase`, `core.filemode=false`), `unseen` reads each tracked file's name and
executable bit from the disk, and one that differs keeps the run off the record, in both
directions. (The plan had also said no commit can carry such a difference: `git mv` and
`git update-index --chmod` do.)

**Round six** (`unseen`: names and executable bits read from the disk where git is set not to see
them): rework — the eight reproductions of round five closed, four more of the same family: a
script committed with LF under `text eol=crlf` (a clone writes CRLF and `/bin/sh^M` fails; the
same with `core.autocrlf` and a clean filter), a name composed in the commit and decomposed on
disk (the comparison folded both), a mode `0654` under `core.filemode=false` (any execute bit was
taken for the owner's), a link kept as a link under `core.symlinks=false`. Each a clean `status`,
a green on record, and `land` or `tag` passing on it once the disk was put back as a clone has
it.

Not taken one by one. Four rounds had each found another way `git status` is no witness of the
disk, and each answer was a list of what git does not see — a list with no end, behind a promise
("a clone passes") that 0.7.28 never made: it ran the suite on this disk. The promise is now the
run's own, and the question the one a record must answer — would a run read other files? — so
`on_disk` replaces `unseen` and the check on `git ls-files -v`: the record holds what the tracked
files were on disk, and any of them written, renamed, re-moded or gone since is a run. In every
reproduction of rounds three to six the green is reused after the disk is changed: none passes.
A seed green on a disk that differs from a clone stays on record while that disk stays as it is
— where 0.7.28 was green three times. Round one's boundary — a file edited and put back
while the suite runs — is seen as well now, unless the writer sets the file's time back.

**Round seven** (`on_disk`; the criterion the one every report had used: 0.7.28 refuses, 0.7.29
passes on a record): rework — the twenty-three reproductions of rounds three to six all refuse
where 0.7.28 refuses; two left, of metadata the hash did not hold: `chmod 555 src` (a suite that
writes a temporary file beside its source fails, the files' own stat unchanged), and a file's
ACL or its count of hard links. Taken: the hash holds each directory's mode on the way to a
tracked file, and the file's links and the time of its last change of any kind (ctime: a mode,
an ACL, a link all move it). The link's target left the hash: lstat's size and times say it.
Also taken: the plan's "it takes a writer that sets the time back" was too strong (a filesystem
of whole seconds), the cost on 10,000 files, the formatter that takes the record of the command
before it; five mutations the tests let through (a directory's spelling, the size apart from the
time, a time under a second, the link itself rather than its target) are pinned.

What held: from `built` through the reviewer's gate to `land` the record stands — reading every
file, `rev-parse`, `diff`, `show`, `status`, an unchanged `add`, a no-op checkout, `mm`'s own
commits and shots, the recovery of a cut publish leave the disk as the run left it.

**Round eight** (directory modes, a file's links and ctime): rework — the nine fixtures of round
seven closed; one more of the family, `chflags uchg src`: an immutable directory, its mode and
its files' stat unchanged, a suite that writes beside its source failing. Taken: a directory's
flags beside its mode. And ctime had no test of its own (taking it out passed every test and
brought the ACL case back): one changes a file without writing it and expects a run.

Measured in this round, with ctime in the hash: reading every tracked file, the git commands the
prompts ask for, an unchanged `add`, a no-op checkout, `built` with its commit and shots, a
second `shot`, the recovery of a cut publish, the reviewer's gate, `land`, Vim opening a file,
copies by `ditto`, `rsync -a` and `tar` — none moves a tracked file's ctime, and the reviewer's
gate and `land` read the record. An extended attribute set on a file does (above).

**Round nine**: ship. The immutable directory closed, ctime and the directory flags each pinned
by a test; the twenty-three fixtures of rounds three to six, the nine of round seven and round
one's file edited and put back (its ctime moves: the run stays off the record) all refuse where
0.7.28 refuses; from `built` through the reviewer's gate to `land` the record is read. What it
could still reproduce is metadata the hash leaves out, with suites written to assert it; no
writer the method allows was shown to produce one in the course of the work — "the builder has a
shell" was withdrawn as a reason by itself. Taken into "Not done": what the hash leaves out, the
output as the last run's, the suite a killed gate leaves behind, and the narrower wording on
changes that write no byte. Its advice, kept: name those limits rather than add fields until the
hash is a snapshot of the filesystem.
