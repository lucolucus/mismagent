# mismAgent 0.5 — the grand design, restarted from theory

> **NON-NORMATIVE DERIVATION RECORD** (2026-09-29, branch `redesign-v1`). How the 0.5 design was
> reached: the evidence, the premises re-examined, the reviews, the experiments. The design itself is
> in three layers: `v0.5-vision.md` (stable), `v0.5-hypotheses.md` (mechanisms, each with its
> experiment), `v0.5-core.md` (the minimal core under test). Where this record and those files
> disagree, those files win.

## 0. Why restart

v0.26.2 does not produce a satisfying engineering flow nor the expected results. The evidence:

| run | app code | test code | process artifacts | cost |
|---|---|---|---|---|
| Cassa6 (v0.24→v0.25.4, finished) | ~3,600 lines | ~4,900 lines | **55,000 words**, 195 files | ~$152 |
| Cassa7 (v0.26.2, stopped at wave 2) | 372 lines | 548 lines | 23,000 words, 70 files | — |
| **Baseline E0** (plain Claude Code, no plugin, R0+R1+R2) | ~1,250 lines | ~1,440 lines | 0 | **$4.95** |

- **The harness talks about itself.** Of Cassa7's 24 frictions, ~20 concern the machinery (decision
  ids, gate-proof hashes, profile fields, pack permissions, waves), 2 the domain model, **0 the
  behavior of the product**. Friction-driven development optimized the smoothness of the process
  (Goodhart), and every fix added surface for the next friction: ten versions in five days.
- **Coordination dominates.** The composer was 73% of Cassa6's build tokens. Blocks, pinned types,
  welds, waves and contract tests exist to make *parallel* building possible; at this scale
  parallelism costs more than it returns (Brooks's law holds for agents).
- **We measured the process, not the product.** No run was ever compared with a baseline (the same
  requirements built without the harness), and the external acceptance was never run on a finished
  build.

**The baseline, run on 2026-09-29** (`bench/scenarios/baseline/`: plain Claude Code, Sonnet, a
15-line `CLAUDE.md`, a simulated user in turns; the same requirements, change request and second
feature as the cassa scenario). R0, R1 with the change request, and the Magazzino feature took ~15
minutes and $3.82 to build (+ $1.13 for the two blind judges: $4.95 in all); the builder asked targeted questions before each release (6, 5, 3), with a
proposal for each. **External acceptance: 40/40 PASS, all 26 🔴.** **Blind code-quality review:
3.1/5** — duplication 2, simple design 3, modularity 3, error handling 3, tests 3; `models.py` a
grab-bag of money, cart and every table's SQL; monolithic window constructors; one error-handling
block repeated ten times; rows read by position; a 706-line GUI test file.

What it proves: **on a small, well-described problem a model alone delivers the features, fast and
cheap.** What it does not do is what the problem did not ask for: no refactoring, no design pass, no
exploration beyond the questions the text raised, no UI research, no existing code to respect —
and a quality already at 3.1 after three releases, the level from which long projects decay.

## 1. The problem a harness solves

A harness compensates for the structural limits of today's agents:

1. **Finite, degrading context** → work comes in units that fit one session; state lives outside.
2. **No memory across sessions** → every session restarts from disk.
3. **Unreliable self-assessment** → a separate checker, grounded in executable evidence.
4. **Drift** (inventing, satisfying the letter, moving the finish line) → "done" fixed before work.

The theory that ties them together is **Peter Naur, "Programming as Theory Building" (1985)**: a
program is the *theory* its programmers hold — why it is the way it is, how it may change. When the
theory dies, the program dies with it, even if the code survives. An agent loses the theory at the
end of every session. mismAgent v0.x tried to externalize the theory into planning documents
written *before* the code (55k words). Naur and XP answer differently:

> **The code carries the theory.** Readable code, tests that tell the behavior, and a short living
> description of language and structure. Not a plan that precedes the code and then diverges from it.

### 1.1 What the harness is for — sharpened by the baseline
Not for getting features out of a well-described problem: the baseline does that at 40/40 for $4.
The harness earns its cost where a single agent, alone, fails over time:
1. **Code that stays maintainable.** Agents write working code that is not clean and decays release
   after release; the harness guides them not to write code that cannot be maintained (§5, §4.4).
2. **Exploration.** Real problems are not well described. The harness drives the investigation of
   the domain (§4.1) and of the **UI** — who uses it, where, under which pressure, what similar
   tools do (§4.1, UI) — before code fixes a wrong understanding.
3. **Existing code.** Most work is brownfield: understand what is there, protect its behavior,
   improve it while changing it (§6).
4. **Guidance, style and coherence across phases** — from the architecture to the design of the
   modules to the code, one line of decisions that every session reads and continues, instead of N
   sessions each with its own style (§4.6).

And it must stay **light by default**: on a small, clear change it should cost close to the
baseline; the depth (exploration, UI research, mapping existing code, design passes) switches on
when the work needs it (§4.7).

## 2. The premises of the old design, re-examined

| premise | where it came from | what happened |
|---|---|---|
| plan vertically, execute horizontally and in parallel (BE∥FE) | human teams: parallelism buys people-throughput | agents' bottleneck is **coherence**, not throughput; parallelism forces interfaces pinned before code, and coordination dominates |
| the executable contract at the center (OpenAPI between two repos) | two deploys, two teams | cross-deploy left in v0.18; the machinery (pinned types, CDC, weld) was transposed onto in-process seams that do not need it |
| decompose by DDD building block (aggregate, port, adapter…) | tactical DDD, hexagonal | a decomposition by **technical layer**: a feature works only when every piece composes → late integration, no running software early (Parnas: decompose by what may change, not by processing step) |
| no premature code — model, then build | Agentheim, BMad | right for the *strategic* level (problem, language, contexts); on the *tactical* level it is Big Design Up Front, while for an agent refactoring is cheap |
| frictions drive the method | continuous improvement | Goodhart: the process gets smoother, the product does not get better |

What **held** on every run: state outside the model · checker ≠ maker · done agreed before work ·
few explicit human checkpoints · the challenger · a gate that can go red · fresh sessions. These
**compensate for agent limits**. What **failed** imitated **human team organization**:
parallelism, contracts between teams, decomposition by technical role.

## 3. Thesis

> **The code carries the theory; the acceptance examples are the pact with the human; the harness
> keeps both honest.**

Foundations, each with one job:

| source | what it gives v0.5 |
|---|---|
| Naur, *Programming as Theory Building* | what must survive a session: the theory, carried by code + a short description |
| XP (Beck), *Simple Design*, TDD; Fowler, *Refactoring*; Beck, *Tidy First?* | the inner loop and the quality standard (§5); design emerges and is continuously improved |
| **Agentheim**, **BMad** — the two ancestors | see §3.1 |
| Specification by Example (Adzic), BDD | the human approves concrete examples, which become executable acceptance tests |
| Event Storming (Brandolini) | the interview's backbone: the domain as a timeline of events, commands, actors, policies, hotspots |
| Event sourcing (as a lens) | every event asked "can it be undone, what remains?" — corrections are events, not erasures |
| Example Mapping (Wynne) | per command: rules → examples → questions |
| Gause & Weinberg, *Exploring Requirements*; Socratic method | probing heuristics and restatement: investigate, don't transcribe; confront options before deciding |
| Cockburn, *Walking Skeleton*; vertical slices | running software from the first slice; integration is never late |
| Strategic DDD (Evans) | ubiquitous language and context boundaries → names and modules |
| Tactical DDD | a **craft reference** applied inside a slice when the code asks for it, never planned upfront |
| Feathers, *Working Effectively with Legacy Code* | brownfield: seams, characterization tests before a change (§6) |
| Parnas, information hiding | modules drawn around what may change, discovered in the design loop |
| Anthropic, *Effective harnesses for long-running agents* | initializer + feature list + progress file + one feature per session + end-to-end tests: the same slice loop, reached from practice |

### 3.1 The lineage: BMad and Agentheim
mismAgent descends from two harnesses and stays their heir; v0.5 goes back to what they do best
and leaves what v0.x over-built on top of them.

**Agentheim** (heimeshoff/Agentheim — "a raw idea into a vision, a vision into a modeled backlog of
bounded contexts, and a backlog into parallel, dependency-aware execution"):

| we keep | in v0.5 |
|---|---|
| *brainstorm* → vision, context map, **walking-skeleton spike** | explore + specify; the skeleton is the first slice |
| DDD: bounded contexts, **ubiquitous language** per context | `glossary.md`, modules named after contexts |
| the **board**: folder = state (`backlog/todo/doing/done`), a read-only dashboard as a projection of disk | `slices/{todo,doing,done}`, `mm status`, the board |
| `protocol.md`, the chronological diary | `progress.md` |
| knowledge injected into the worker (context READMEs, index, ADRs, research) | the builder reads `ARCHITECTURE.md`, glossary, progress, ADRs first |
| worker in **red-green-refactor**; a **fresh-context verifier** before the commit; one unit = one commit after PASS | builder + reviewer; slice lands only after PASS |
| *research* checked by a fresh *research-reviewer* before it is cited | research on demand, same rule |
| *inquire* ("what was decided and why") and *whats-next*, read-only | worth porting as-is: cheap, and they serve the human |

What we leave: the tactical backlog modeled before code, and parallel execution by default.

**BMad** ("turn an idea or change request into working software without giving up the thinking"):

| we keep | in v0.5 |
|---|---|
| the delivery loop **Clarify → Plan → Build and verify → Learn and adjust** | intent → slices → the design pass (§4) |
| **right-sized process**: a clear change goes straight to build, larger work gets deeper planning | depth follows the work (§4.7) |
| **specialized perspectives** — analyst, product, architecture, UX, development, test | specify (analyst + product), UX exploration, architect, builder, reviewer |
| **advanced elicitation** and **party mode** — structured methods to push past the first answer, several perspectives debating | the investigative interview (§4.1) and the confrontation of advocates (§4.5) |
| the context file kept minimal: "agents read code better than prose about code, and the copy goes stale" | Naur: the code carries the theory; `ARCHITECTURE.md` short and rewritten from the code |
| in an existing codebase, build "looks at the code first, and stops to ask when it cannot settle the intent" | the brownfield entry (§6); in doubt, stop and ask |
| the **retrospective** | the design pass learns from the slices; frictions about the product |

What we leave: the long document chain (PRD → epics → stories) as the carrier of intent — examples
and code carry it instead.

## 4. The four loops

```
 ┌─ INTENT (the human) ──────────────────────────────────────────────────┐
 │ requirements → brief (challenged) → EVENT STORM → EXAMPLES → slices   │
 │ ✋ the human approves examples and the release cut, and picks the stack │
 │                                                                        │
 │  ┌─ SLICE (one builder, one fresh session, strictly in sequence) ───┐  │
 │  │ walking skeleton first, then one vertical slice at a time         │  │
 │  │ (1–3 examples, end to end through the real app);                  │  │
 │  │ order: risk first, then value                                     │  │
 │  │                                                                   │  │
 │  │  ┌─ CRAFT (inside the session) ───────────────────────┐           │  │
 │  │  │ acceptance test red → TDD → green → refactor →      │           │  │
 │  │  │ commit at every green                               │           │  │
 │  │  └─────────────────────────────────────────────────────┘           │  │
 │  │ done = the slice's examples green + every earlier one green       │  │
 │  │        + a fresh reviewer who RUNS the app and reads the tests    │  │
 │  └───────────────────────────────────────────────────────────────────┘  │
 │                                                                        │
 │  ┌─ DESIGN (every N slices, or on a signal) ──────────────────────────┐ │
 │  │ a fresh architect reads the CODE → rewrites ARCHITECTURE.md →      │ │
 │  │ queues refactoring slices (behavior preserved: the suite stays     │ │
 │  │ green)                                                             │ │
 │  └────────────────────────────────────────────────────────────────────┘ │
 │ ✋ release: the human sees the app running and accepts                  │
 └────────────────────────────────────────────────────────────────────────┘
```

### 4.1 Intent
- **explore** (in session with the human): problem, users, value, scope cut → `brief.md`. The
  **challenger** (fresh context) tries to demolish it first. Kept almost as is.
- **specify — an investigation, not a transcription** (in session with the human). The
  interviewer's stance is the detective's and the senior process engineer's: it does not validate
  what the human tells, it **investigates** — it looks for what is missing, what contradicts, what
  nobody said because it seemed obvious. It argues the devil's advocate on every rule, and it asks
  **specific** questions ("the operator has typed three items and the power goes: what is on the
  receipt when the till restarts?"), never generic ones ("any edge cases?"). It uses proven
  techniques, in this order:

  1. **Event Storming** (Brandolini), process level, conducted in text. The agent rebuilds the
     domain as a **timeline of domain events** in the past tense ("Sale opened", "Item added",
     "Payment received", "Day closed"), then fills each one in: the **command** that causes it, the
     **actor** who issues it, the **policy** that reacts to it ("whenever a day is closed, the
     report is printed"), the **read model** someone looks at to decide, the **external system**
     involved. Every doubt, conflict or gap becomes a **hotspot** — the interview's agenda.
  2. **The event-sourcing lens** on every event: *can it be undone? by whom? what remains of it?*
     A correction is a new event, never an erasure — that question alone surfaces refunds, voids,
     audit and end-of-day invariants a narrative skips. Whether the code is then *built* event
     sourced is a stack decision, offered to the human when the domain is a ledger.
  3. **Example Mapping** (Wynne) on each command and policy: the **rules** it obeys, **concrete
     examples** for each rule, with real numbers ("2 coffees at €1.20, paid €5 → change €2.60"),
     and the **questions** nobody can answer yet. A rule with no example is not understood; a rule
     with too many examples is two rules.
  4. **Probing heuristics** (Gause & Weinberg, *Exploring Requirements*; the detective's method)
     applied to every hotspot: the boundary value and the one past it · the empty case · the error
     and the recovery (crash, power loss, a half-done operation) · the whole lifecycle of each thing
     (created, changed, retired — and who may do each) · time (end of day, month, year, a clock
     change) · money (rounding, currency, totals that must reconcile) · two requirements that
     disagree · the thing that is created but never deleted, or read but never written · the role
     that is never mentioned · volumes and speed at the counter · the law or rule outside the
     software.
  5. **Socratic restatement.** The agent restates each rule in the human's words and asks for the
     counter-example ("so a sale can never be modified once paid — not even to fix a wrong
     price?"). A term that changes meaning between two answers goes to the **glossary**
     (strategic DDD: terms and contexts, one page); a boundary between contexts shows up as a
     place where the same word means two things.

  The human confirms, corrects or cuts. What survives becomes: `event-storm.md` (the timeline with
  its commands, actors, policies, read models, resolved hotspots), `examples.md` (one row per
  example: id, given, when, then, rule, requirement — falsifiable) and open questions, never
  guesses. The storm also gives the **slice plan** almost for free: a slice is one path through the
  timeline, command → events → the read model that shows it, end to end. The agent proposes it —
  the walking skeleton first, then slices ordered by risk and value, each naming its examples — and
  the human confirms. Releases = cuts of the slice list. In a headless run the simulated user
  answers from its policy and oracle, as today.

  **In waves, never all at once.** The storm and the glossary cover the whole product at process
  level (cheap: events and hotspots, no detail); examples, mockups and the slice plan are made
  **only for the next release**, right before it is built, and the next release's investigation
  starts from what the code and the users taught. Specifying everything upfront would bring back
  the 55k words.
- **UI exploration** (when the product has a user interface). The same investigative stance on the
  interface: who uses it, where, with which skills, under which pressure (a queue at the counter,
  gloves, a small screen); what similar tools do well and badly (research on demand); the storm's
  read models become **screens**, its commands become **actions** on them. The agent proposes one
  or two **low-fidelity mockups** of the main screens (static HTML or ASCII, cheap to throw away),
  the human reacts, and the approved ones join the examples: a UI example says what the user sees
  and does, and is proven by driving the real interface. Principles and decisions that must hold
  on every screen (layout, sizes, colors, wording, error style) go to a short **UI guide** in
  `ARCHITECTURE.md`, so every slice builds the same interface.
- **stack**: chosen with the human once, before the skeleton; recorded as the first ADR. The only
  architecture decided upfront is what is expensive to reverse (language, UI toolkit, persistence,
  deploy target).

### 4.2 Slice
One **builder** per slice, fresh session. It reads, in this order: `ARCHITECTURE.md`, `glossary.md`,
the tail of `progress.md`, its slice file, then the code it will touch. It:
1. writes the slice's acceptance tests first, from the approved examples (red for the right reason),
   **at the use-case seam** — the application's own entry points, below the interface — plus a thin
   smoke test that the screen reaches that seam. Tests bound to widgets freeze the structure and make
   refactoring expensive; tests at the seam force a core free of the UI;
2. works the craft loop until they are green, keeping every earlier test green;
3. commits at every green step (a cut session loses little);
4. appends a short `progress.md` entry: what changed, what it learned, what the next slice should know.

A doubt it cannot settle from the files → it writes it in the slice file and returns; the
conductor resolves it (§4.5). It never guesses.

One **reviewer** per slice, fresh session:
- runs the whole suite (the app itself is run at each release, not at each slice);
- checks each acceptance test really proves its example (not a weaker one) — checker ≠ maker;
- reads the diff for defects against `ARCHITECTURE.md` and the craft references;
- returns `PASS` or `REWORK` with findings in a file. A defect blocks the slice when it breaks an
  example, loses data, or violates the quality standard (§5) in the slice's own diff (max two
  rework rounds, then the architect decides by the standard). What reaches beyond the diff goes to
  `design-notes.md`, the design loop's inbox — **no waiver ledger**: a defect *in* the diff can never
  be routed there.

On `PASS` the slice branch fast-forwards onto the main line: slices run in sequence, so the line is
never red and there is nothing to compose.

### 4.3 Craft
The inner loop is the existing `craft` skill (TDD, refactoring, simple design, clean code, SOLID,
frugality) plus a new **tactical DDD reference**: aggregates, invariants, value objects, domain
events — *when the code asks for them* (an invariant spread over two places, a primitive that keeps
being validated, a rule that needs a single owner).

### 4.4 Design
When a signal fires — never on a fixed cadence — a fresh **architect** runs a design pass. The
signals: the **rubric score** taken at each release (a cheap blind review on the rubric of §5,
under a dollar) has a dimension below 4; the sensors crossed a threshold; `design-notes.md` holds
more than a few items; a slice had to touch many modules. The architect:
- reads the code, not the plan;
- rewrites `ARCHITECTURE.md` (≤ ~800 words: modules and what each hides, dependency directions,
  where the invariants live, conventions) and compacts `progress.md`;
- turns `design-notes.md` into **refactoring slices** (behavior-preserving, the suite stays green)
  queued before the next feature slice, and clears the notes it consumed;
- records an ADR only for a decision that is expensive to reverse.

Conventions are **stable**: a design pass describes the code truthfully, but it does not flip a
convention (error style, test shape, how a window is built) silently — a change of convention is a
decision recorded in `ARCHITECTURE.md`'s change log with its reason, and the refactoring slices
that apply it everywhere, so no two conventions live side by side.

This is where the "theory" is curated. It replaces upfront pinning, the composition block, the
release layers and the harvest skill. The snastro design review found more real problems than all
the upfront pinning did; v0.5 makes that review a loop of the method.

### 4.5 Doubts — resolved by confrontation, important ones brought to the human
A doubt raised by a builder, a reviewer or the architect is the conductor's to resolve. It does not
guess and it does not forward everything to the human: it runs a **Socratic confrontation**.
1. **Frame it.** The question, what depends on it, and what the files already say (examples, event
   storm, glossary, ARCHITECTURE.md, ADRs). Often the answer is there and the doubt closes here.
2. **Confront the options — only at a real fork, and at most one round.** The conductor first
   writes the options and its recommendation; only when the fork is important and the
   recommendation is not clear-cut does it call the advocates — at least two concrete options, each argued by a fresh-context agent
   as its advocate and attacked by the other — the challenger's pattern applied to a decision:
   *what does this option assume? which example or rule does it break? what does it cost to
   reverse?* The conductor asks the questions and weighs the answers against the evidence; it does
   not hold the debate in its own context.
3. **Classify, then act.**
   - **Important** → brought to the human, with the options, the strongest argument for each, and
     the conductor's recommendation. Important means: it changes what an example or rule means,
     the scope, the money, the stack or an expensive-to-reverse structure, anything outward-facing,
     or the two options stay balanced after the confrontation.
   - **Local and reversible** → decided by the conductor, recorded in `progress.md` (question,
     options, choice, why), and the slice resumes. The design loop revisits it.
4. **Record.** Every doubt leaves one short entry — in `decisions/` if it constrains later work, so
   compacting `progress.md` never loses a "why"; an important one that the human decides and that
   is expensive to reverse becomes an ADR.

Quality disputes never go to advocates: after two rework rounds the architect decides by the
standard. The cost of doubts is measured per slice; if it grows, the builder's threshold for raising
one is wrong, not the rule.

### 4.6 Coherence across levels — from architecture to design to code
One line of decisions, each level written once and read by the next:

| level | decided when | lives in | read by | kept coherent by |
|---|---|---|---|---|
| intent: problem, language, events | specify | `brief.md`, `glossary.md`, `event-storm.md` | everyone | the conductor (doubts), change requests |
| architecture: stack, style, deploy | before the skeleton, with the human | ADRs | architect, builder | superseding ADRs only |
| design: modules, what each hides, dependency directions, where invariants live, UI guide, conventions | the skeleton, then every design pass | `ARCHITECTURE.md` | builder, reviewer | the architect, from the code |
| code | every slice | the code and its tests | every later slice | sensors, reviewer, refactoring slices |

Every builder reads the levels above its code before writing it; every reviewer checks the diff
against them; the architect rewrites the design level **from the code** so the description never
lies. **Style is a decision, not an accident**: conventions (naming, error handling, how a window
is built, how a query is written, how a test is shaped) are written once in `ARCHITECTURE.md`,
enforced by sensors where computable, and the first time a slice meets a new kind of code it sets
the pattern the next ones follow.

**The exemplary slice.** The walking skeleton carries one feature built end to end *as a model*: one
screen, one use of the domain, one query, one error path, one acceptance test and one unit test,
each written the way every later one should be. The reviewer holds the skeleton to the highest bar,
and `ARCHITECTURE.md` points to it ("a new window looks like this"). Style spreads by imitation —
cheaper and stronger than any page of conventions; the baseline's duplication (ten copies of one
error handler, five of one table setup) is exactly what a missing model produces. A conflict between levels is a doubt (§4.5), never a silent
divergence.

### 4.7 Depth follows the work — light by default
The flow is always the same four loops; how much of each runs depends on the signals:
- a **small, clear change** on known code → one slice: builder + reviewer (+ the sensors). Close to
  the baseline's cost.
- **unclear or conflicting requirements**, a new domain → the full specify investigation (storm,
  example mapping, probing).
- **a user interface** that is new or changes shape → UI exploration.
- **existing code** not yet mapped → the brownfield entry (§6).
- **structure signals** (sensors past thresholds, design notes piling up, a slice touching many
  modules) → a design pass.

**Who decides the depth: the intake.** Every request — a new product, a change request, a second
feature — enters through a short intake (the first step of explore/specify): it reads the request,
the repository (is there code? tests? an `ARCHITECTURE.md`?) and asks the human two or three
questions, then proposes the depth (which of the above apply) with a cost estimate; the human
confirms or changes it. In a headless run the simulated user's policy fixes the answer. The
conductor only applies it and adds a design pass when the build's own signals fire.

## 5. Code quality — a fixed point

Working software is not enough. The code must be **clean, concise and well structured, to XP's
standard** — and this is not a nicety: only clean code can carry the theory (Naur). Messy code that
passes its tests is a program whose theory is already dying.

**The standard** — one definition, used by the builder, the reviewer and the architect:
- **Beck's four rules of simple design**, in priority order: passes the tests · reveals intention ·
  no duplication (once and only once) · fewest elements.
- **YAGNI:** nothing for a future slice — no speculative generality, no unused parameter,
  abstraction, option or layer.
- **The domain speaks:** names come from the glossary; a name that needs a comment is a wrong name.
- **Small, cohesive units:** a function does one thing at one level of abstraction; a module hides
  one decision that may change (Parnas) and depends only in the directions `ARCHITECTURE.md` states.
- **Concise:** the smallest correct program wins; deleting code is progress; dead code is removed,
  never commented out.
- **Tests are code too:** one behavior each, named as the behavior, fast, no sleeps, readable as
  documentation.
- **A coding standard:** the stack's conventional formatter and linter, zero warnings.

**The review table.** The seven dimensions the blind review scores (simple design · naming and
domain language · modularity and dependencies · duplication · concision · error handling · test
quality), each with concrete anchors for 3, 4 and 5, are the **reviewer's** table (and the
architect's, who reviews the design): whoever reviews code reviews it on the same table it will be
judged by (the user's call, 2026-09-29). The builder works from the standard above, not from the
scores. Against Goodhart — code that pleases the table without being easier to change — the
measure that decides is not the table but **the cost and the defects of the next change** (§13, S2);
the table is its proxy.

**Structure is decided at birth, not refactored in later.** The design-pass experiment (§13) moved
duplication, simple design and tests from 3 to 4, but left **modularity and error handling at 3**: a
post-hoc refactoring cleans, it does not decide. So the skeleton — written by the architect with
the first builder, approved by the human with the stack — fixes:
- **the layering and its dependency lint**: the domain imports neither the UI nor the database; one
  module owns each table (never two modules writing the same table); the UI talks to use cases;
- **the error policy**, as an ADR: the domain raises typed errors meant for the user; one boundary
  in the UI translates, logs and shows them; unexpected errors are logged and surfaced, never
  swallowed; lookups of a missing thing fail explicitly;
- **the exemplary slice** (§4.6) and the sensor thresholds.

**How it is held** — sensors before judgement, and paid while it is small:
1. **Sensors, in the gate** (computed). Wired by the walking skeleton with the stack's standard
   tools: formatter, linter at zero warnings, a dependency lint of the module directions in
   `ARCHITECTURE.md`, size and complexity thresholds (function, file), duplication detection. They
   turn the gate red like a failing test. Few thresholds, in the project's `CLAUDE.md`, tightened
   over time, never relaxed to let a slice pass. A **suppression sensor** counts lint-disable and
   `noqa` lines and diffs of the thresholds: if they grow, the gate is red.
2. **Craft, in the builder.** Refactoring is a step, not an option: no slice is returned after the
   last green without a refactoring pass over its diff against the four rules, and the code it
   touched is left cleaner than it was found — within the slice's scope.
3. **Judgement, in the reviewer and the architect.** The reviewer judges what sensors cannot:
   intention, naming, the wrong abstraction, a responsibility in the wrong module, a test that does
   not say what it proves. **A quality defect in the slice's own diff blocks the slice**, exactly
   like a functional one — there is no "medium, later". To keep this from turning into endless
   nit-picking, a blocking finding must **name the rule of the standard it breaks and the line**;
   taste is advice, never a block; at most two rework rounds, then it is a doubt (§4.5). What reaches beyond the diff (a pattern
   across modules) goes to `design-notes.md`; the architect turns it into refactoring slices that
   run **before** the next feature slice. The inbox is bounded: past a few items, the next slice is
   a design pass.

**Guards on what belongs to the human.** The requirements, `examples.md` and the acceptance tests
are the human's side of the pact: a hook refuses edits to them outside specify (the baseline's
design-pass builder rewrote a column of the requirements file). Otherwise traceability could be
satisfied by editing the example instead of the code.

XP's practices, mapped: **pair programming** → the builder and a fresh reviewer on every slice;
**collective ownership** → any slice may improve any code, the architect keeps it coherent;
**continuous integration** → every slice lands green on the main line; **coding standard** → the
sensors; **refactoring** → inside every slice and as scheduled slices; **simple design** → the
standard above; **small releases** → a release is a cut of the slice list.

## 6. Existing code and changes of intent

**Brownfield entry** — a codebase the harness has not built (or has not mapped yet). Before any
change, a fresh architect does an **archaeology pass** (Feathers, *Working Effectively with Legacy
Code*; Naur: recover the theory before touching the program):
1. reads the code and writes `ARCHITECTURE.md` **as it is** — modules, dependencies, where the rules
   actually live, conventions actually followed, the worst problems — and a glossary from the
   code's own names, noting where they disagree with the domain's;
2. with the human, rebuilds the **event storm of the existing behavior** (what the system does today)
   next to the one of the change;
3. before a slice modifies code without tests, **characterization tests** pin its current behavior —
   the change is then made under that net, and the touched code is left cleaner (the boy-scout rule
   of §5, bounded to the slice);
4. structural debt that blocks the change becomes refactoring slices first; the rest goes to
   `design-notes.md`. The sensors start **at the current level** and only tighten (a legacy file is
   not a red gate; making it worse is).

**Changes of intent** — a change request or a second feature re-enters at **specify**: new or
amended examples (the amended ones are marked), new slices; the architect first maps which code the
change touches. The acceptance suite is the regression net: an amended example turns its old test
red, and the slice that fixes it is ordinary work. Existing code is an input by construction —
there is only one codebase and every builder reads it.

## 7. Artifacts — everything the project holds

```
<repo>/
  ARCHITECTURE.md            # the theory: modules, what they hide, dependencies, conventions (≤ ~800 words)
  CLAUDE.md / AGENTS.md      # commands: test, acceptance, run, lint (the profile shrinks to this)
  tests/acceptance/          # one test per example, named by the example id
  .mismagent/
    brief.md                 # problem, users, value, scope — challenged
    glossary.md              # ubiquitous language + contexts
    event-storm.md           # timeline: events, commands, actors, policies, read models, hotspots
    examples.md              # the approved examples, each tagged with requirement + slice
    slices/{todo,doing,done}/NN-<name>.md   # folder = state; goal, example ids, open question
    progress.md              # append-only session log, compacted by the architect
    design-notes.md          # the design loop's inbox
    decisions/               # ADRs: only the expensive-to-reverse choices
```

Budget: process artifacts stay **well under the code in size** (target for a Cassa-sized app:
≤ 6k words in `.mismagent/`, against 55k today). A document without a reader is not written.

## 8. The tool

Tools compute, agents judge. `mm` shrinks from ~3,400 lines to a few hundred:
- `mm status` — slices per folder; examples ↔ tests traceability (every approved example has a test
  named by its id; every acceptance test names an approved example); last suite result.
- `mm next` — the next slice (a queued refactoring first), or the reason there is none (an open
  question, a failing suite, the release point).
- `mm move <slice> <state>` — the only state write, done by the conductor.
- `mm check` — lint of the files above (examples tagged, slice files well formed, sizes within budget).
- Suite results come from the test runner's JUnit-XML report, which almost every stack can emit —
  no per-stack parsing in the core.

## 9. Roles

| role | context | writes |
|---|---|---|
| explore (skill, main session) | with the human | `brief.md` |
| challenger (agent) | fresh | its verdict |
| specify (skill, main session) | with the human, investigating | `event-storm.md`, `glossary.md`, `examples.md`, slice files, first ADR |
| conductor (`/mismagent:build`) | fresh per firing | slice state (`mm move`), merges, doubt records |
| advocates (agents, on a doubt) | fresh, one per option | their argument |
| builder (agent) | fresh per slice | code, tests, `progress.md` entry |
| reviewer (agent) | fresh per slice | review file, `design-notes.md` |
| architect (agent) | fresh per design pass | `ARCHITECTURE.md`, refactoring slices, ADRs |

The **conductor** is the orchestrator — the heir of the worker-composer. Two jobs:
- **the cycle**, pure plumbing: `mm next` → dispatch the builder → dispatch the reviewer → merge +
  `mm move`; every N slices the architect. It does not read code or review it.
- **the doubts** (§4.5): it frames each one, runs the confrontation through fresh-context advocates,
  decides the local ones and brings the important ones to the human with a recommendation.

`mm` computes, the agents build and review, the conductor keeps the flow and settles doubts; the
debates happen in fresh contexts, so its own session stays short. It is the only writer of state
and of the main line. It is a thin slash command
(`/mismagent:build`), usable interactively, under `/loop`, or headless under `bench/run.py`.

## 10. Human checkpoints
1. the challenger's verdict on the brief;
2. the stack;
3. the **examples** and the release cut (the main one: here the human says what "right" means);
4. an **important** doubt, after the confrontation (§4.5), with options and a recommendation;

## 13. How v0.5 is judged

Against the **product**, in this order of weight:
1. external acceptance by a blind judge (`acceptance.md` A01–A40, written before any run);
2. **code quality and architecture**: a blind senior review of the final code (the snastro review,
   made a phase of the scenario) plus the sensors' numbers (size, complexity, duplication, lint);
3. **the cost of the change request** (scenario phase C): how cheap it is to change what was built —
   the operational measure of a live theory;
4. human attention (number of questions);
5. dollars;
6. process artifacts vs code size.

Everything **against the baseline**. E0 (§0) set the floor on the cassa scenario: 40/40
acceptance, quality 3.1/5, $4.95. **A design pass on E0's code** (a fresh architect writes
`ARCHITECTURE.md` and 12 refactoring steps, a builder executes them with the suite green; the
architect never saw the quality report): **$3.39, quality 3.1 → 3.7**, acceptance still 40/40 —
duplication 2 → 4, simple design and tests 3 → 4, **modularity and error handling unchanged at 3**.
The loop works and is cheap; it plateaus below 4 on what only a decision at birth fixes (§5).

**Order of the experiments** — cheapest falsification first:
0. **The judge's noise** (~$3): the blind review three times on E0's R2 code and three times on the
   design-passed code. If the spread is ~0.4 or more, "3.7 vs ≥ 4" is not measurable with one
   review, and every score below is the mean of three.
1. **S2-lite — the main bet** (`bench/scenarios/long-horizon/`): four change requests written in
   advance and fully specified (sconti, pagamento misto e storno, listini, chiusura ed esportazione:
   each touches the cart, the payment, the sales and the reports again), in three arms —
   **A** the baseline continuing from its R2; **C** A plus one post-hoc design pass after each
   release; **B** the minimal core of v0.5 (structure at birth, error policy, rubric-aware builder
   and reviewer, sensors with the suppression count, design pass on signal; no advocates, no
   storm), built from scratch through R2 and then the same four requests. After every release:
   the rubric score (mean of three), the cumulative acceptance, the dollars. **The bet is falsified**
   if B is below 4 after the last request, or B's quality slope is not flatter than A's, or B
   costs more than ~4× A per request, or C ≈ B (then the per-slice machinery buys nothing over one
   cheap cleanup).
2. Only if B survives: the rest of the design, each part against its own scenario.

The scenarios: The cassa scenario alone cannot tell a good method from none on
features; it can on quality. So v0.5 is judged on:
- **cassa (well described)** — acceptance stays 40/40, **quality ≥ 4**, cost within a few times the
  baseline's (target ≤ $20), not forty times;
- **S1 — vague requirements**: the same product from a short, incomplete, partly contradictory
  brief, the full requirements held by the simulated user as its oracle: how many of the oracle's
  hotspots each flow discovers before building, and the acceptance on the full requirements;
- **S2 — long horizon**: four or five change requests in sequence on the same code; quality and the
  cost of each change, release after release (does the curve stay flat or climb?);
- **S3 — brownfield**: start from the baseline's own R2 code (quality 3.1, no harness artifacts) and
  add a feature; behavior preserved, quality after the change;
- **S4 — UI**: a product whose value is in the interface, judged by a UI-focused blind review.

Each scenario is pre-registered (hypotheses, phases, budgets, acceptance written before the run)
and run **twice: baseline and v0.5**. A component of the old design returns only if one of them
shows a failure it would have prevented.

Friction logging changes too: it records what went wrong **in the product or the human's
experience** (a wrong behavior, a question asked twice, a slice that broke earlier work), not every
rough edge of the tool.
