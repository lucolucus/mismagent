# 0.7.25 plan — the release review checks by category; a process log

Two changes from the 2026-10-30 review of 0.7.24 (design vs BMad/Agentheim + usefulness from the
real runs). Each names the number it should move, so it can be kept or reverted on evidence.

## Why

- **Release review has no scope.** `mismagent-reviewer.md` (release, step 2) asks for "all seven
  dimensions on the code the release touched". In practice it samples: wiki_planet `R0-1` says
  "Assessed from gate, structure and file sizes, not a line-by-line read of every file", and its
  findings are look differences (R0: 4 rounds, all DESIGN-PASS; 8/20 REWORK look-only). What only a
  release can see — the cross-cutting rules along the production path (one error boundary, security
  on every adapter, wiring through the composition root), the gate actually running the tests (the
  recurring false green: Sagra, snastro, p7read) — has no explicit place.
- **No record of the method's friction.** Code problems go to `design-notes.md`; the method's own
  friction (unclear example, `mm` refusal, missing SDK, context `/clear`) is collected by nobody
  since `MISMAGENT-LOG.md` was dropped. And there is no data to measure the method with: no $, no
  minutes, no human answers per slice (the review's main finding: "useful" is unmeasured).

## A. Categories of the conventions topics

**Project skill format** (`.claude/skills/conventions/SKILL.md`): `## Kinds` splits into three
sections; `## Practices` unchanged.

| section | what | slice review | release review |
|---|---|---|---|
| `## Kinds — local` | a kind of file: entity, use case, screen state, view, adapter, fixture | line by line on the diff (as now) | only the hotspots: the 10 source files (code extensions, tests excluded) touched by most slices of the release |
| `## Kinds — cross-cutting` | rules that span files: errors, security, configuration, composition root, naming, project layout, logging | on the diff (as now) | **every topic, one traced path each**: the path of the smoke or of a release example's use case where the topic applies; the line cites the files read (`file:line` of the boundary, adapter, root) or says `not traced` |
| `## Kinds — tests` | acceptance, unit, ui, shot tests | on the diff (as now) | the gate ran each acceptance file (the test names in its output), markers ↔ examples, no test skipped/disabled |
| `## Practices` | how the work is done | as now | not checked |

Default for a new topic: local; cross-cutting when its rules concern files of more than one kind.

**mm.py**
1. `run_check`: parse the project SKILL.md with `sections()`; headings matched by
   `^kinds\s*[—–-]\s*(local|cross-cutting|tests)$` (case-insensitive). Topic links found as
   `references/[\w./-]+\.md` in each section body.
   - SKILL.md has a categorized section → **error** for a kind topic (every `references/*.md`
     file on disk, not under `practices/` — walk-based, so an unlinked topic is an error too)
     listed in no category or in more than one; error for a plain `## Kinds`
     beside categorized ones.
   - SKILL.md has only a plain `## Kinds` (every existing project) → one **warning**:
     "kinds not categorized: /mismagent:conventions splits them". No red gate on upgrade.
2. Look accepted on the record: the release review's last block gains `LOOK: <n> pairs differ`;
   `mm review` stores the line in the review file; `mm tag` requires `--why` when the review at
   HEAD is DESIGN-PASS **or** has `LOOK:` > 0 (`accepted()` writes the decision for both).
3. Docstring: the skill format line, `LOOK:`.

**Prompts**
- `skills/conventions/SKILL.md` §3: the three sections; §2: each create proposes a category
  (the human confirms in the same table); a plain `## Kinds` found → propose the split as the
  first table (one answer accepts it).
- `agents/mismagent-architect.md`: skeleton step 5 and catalog step 2 — each `- now create` line
  carries `[local|cross-cutting|tests]`; the list in step 5 already names the cross-cutting ones.
- `agents/mismagent-builder.md` §4: a proposal carries its category.
- `agents/mismagent-architect.md` design-pass step 2: a look difference is no longer an open
  question in the release file; the pairs are left for the human at confirm (the `LOOK:` line).
  A behavior difference stays an open question.
- `agents/mismagent-reviewer.md` top (l. 16): "the cross-cutting ones … security, errors, tests"
  → the cross-cutting and tests topics.
- `agents/mismagent-reviewer.md`, release review step 2 rewritten:
  1. tests topics: the gate output names each acceptance file of the release's examples;
  2. each cross-cutting topic: its Must/Never along **one** traced path (the smoke's, or a
     release example's use case where the topic applies) — the line names the files read, with
     findings or "nothing"; `not traced` (and why) is allowed and honest, "checked" without files
     is not a check;
  3. local topics: the hotspots only (`git log --name-only` over the release's slices: the 10
     source files touched by most slices);
  4. the seven dimensions stay the frame of the verdict: each finding names its dimension;
  5. **look pairs**: listed and named (same / what differs) as now, but a look difference alone
     is **not** a DESIGN-PASS cause — counted in `LOOK:`, accepted by the human with `--why` at
     confirm. A difference an example quantifies (a contrast ratio, a size in an example's
     `then`) is an example failure: blocking as before. Slice review unchanged (a look
     difference there stays blocking).
  Uncategorized skill (warning) → as today, all topics treated as local + the seven dimensions.
  Draft checklist format: one line per category topic (`errors: checked, nothing` · findings).
- `skills/craft/references/review-table.md`: the release paragraph points to the categories.

## B. The process log — minimal: no new state file

Categories: `spec` (example unclear, missing, contradictory) · `tool` (mm, gate, hooks) ·
`conventions` · `env` (SDK, CI, device, network) · `context` (too big, lost, /clear) ·
`review` (a REWORK the builder thinks wrong) · `none`. Note ≤ 15 words.

**mm.py**
1. `mm built <slice> --friction "<category>: <note>" | --friction none` — **required**; the
   parser gains the option like `review`'s. Validated **before** the gate (unknown category,
   > 15 words → refused at once). Written as a header line `Friction: <round>: <category>: <note>`
   in the slice file, which `mm built` already commits — one line per round.
2. `mm review … --friction "<category>: <note>"` — optional; written as `FRICTION:` beside
   `VERDICT:`/`SHA:` in the review file `mm review` already writes (committed by `land`/`tag`
   as today).
3. `mm log [--json] [--release R]` (new, read-only, this repo): reads the `Friction:` lines of the
   slices and the `FRICTION:` lines of the reviews; prints the count per category (and % of
   built rounds), then the notes grouped by category (`none` omitted); and per landed slice,
   computed from git at read time: rounds (reviews of the slice), doubts (`## Answer` sections —
   the conductor's local answers included, so "doubts", not "human answers"), wall-clock from the
   `Base:` commit time to the `mm land` commit (labelled wall-clock: it measures the calendar,
   not the work). Median and p75 of each.

**Prompts**
- `agents/mismagent-builder.md`, Return: the `mm built` line gets `--friction`: "what in the
  *method* slowed you this round — not the code (that is `design-notes.md`) — or `none`;
  `none` is the normal answer".
- `agents/mismagent-reviewer.md`, Output: `--friction` when the method (not the code) got in
  the way of the review.
- `commands/build.md`, `confirm`: before `NEEDS-HUMAN: confirm`, print `MM log --release <R>`
  totals (counts per category, median rounds) — 3 lines.
- Root `README.md` only: the log, and the rule: **read it at a release with the counts; change
  the method only for a recurring category, naming the number the change should lower.** Not a
  to-do list of single entries. This plan follows the rule too: more log machinery only if the
  counts ask for it.

## Not in this version

separate process-log file; multi-repo `mm log` (run it in each project); cost in $ (no reliable
source in the plugin); any change to the slice review.

## Tests (`tools/tests/test_mm.py`)
- check: categorized skill ok; topic on disk in no category → error; in two → error; plain
  `## Kinds` → warning only; practices untouched; `Kinds - local` (hyphen) accepted; the real
  SKILL.md shapes of wiki_planet and p7read (links with and without backticks).
- built: missing `--friction` → usage error; unknown category / 16 words → refused **without
  running the gate**; `none` → `Friction: 1: none` line; a rework adds `Friction: 2: …`; the 17
  existing `built` calls pass `--friction none`.
- review: `FRICTION:` and `LOOK:` lines stored; tree still clean for `land`.
- tag: `LOOK:` > 0 on a HEALTHY review → refused without `--why`, decision written with it.
- log: counts, grouping, rounds/doubts/wall-clock per landed slice, `--release`, empty repo.
- prompt_lint green; full suite green.

## Measure (decides keep/revert at the next two releases, wiki_planet R1/R2 or meterbb R3)
Not "look-only DESIGN-PASS → 0" or "rounds to HEALTHY": A's rule change lowers those by
definition.
- A: per release review, cross-cutting findings **with a traced path** and how many were later
  fixed by a slice (real) vs dropped; false greens caught by the tests category (the kind of
  wiki_planet R0-4 finding 1, `scripts/test.sh`); `not traced` lines (if most are, the scope is
  still too wide).
- B: share of `none` (if > 90% over 20 slices, `--friction` becomes optional); the top category
  and whether it was already known. `context` reads ~0 by construction (a builder cut by its
  context never reaches `mm built`): not evidence of anything.
