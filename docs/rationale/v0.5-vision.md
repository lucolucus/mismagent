# mismAgent 0.5 — the vision

> **Layer 1 of 3 — stable.** Changes only by the user's choice. Budget: ≤ 2,500 words.
> Layer 2: `v0.5-hypotheses.md` — every mechanism, with the problem it answers and the experiment
> that confirms or refutes it. Layer 3: `v0.5-core.md` — the minimal core under test.
> How we got here (evidence, reviews, experiments): `v0.5-derivation.md`, non-normative.

## 1. What the harness is for

A single agent, given a small well-described problem, already delivers the features: the baseline
(plain Claude Code) built the cash register, its change request and a second feature in fifteen
minutes for $4, and passed 40/40 of an external acceptance. What it loses is what the text did not
ask for: its code scored 3.1/5 on quality after three releases, with no refactoring, no design, no
exploration beyond the obvious questions, no UI research, and no existing code to respect.

mismAgent is for the long, complex projects where that loss compounds. It guides agents to:
1. **write code that stays maintainable** — clean, concise, well structured, release after release;
2. **explore** — investigate the domain and the user interface before code fixes a wrong
   understanding;
3. **work in existing code** — recover its theory, protect its behavior, improve it while changing it;
4. **stay coherent** — one line of style and decisions from the architecture to the design of the
   modules to the code, across every session.

And it stays **light by default**: on a small, clear change it costs close to the baseline; depth
switches on when the work needs it.

## 2. Thesis

> **The code carries the theory; the acceptance examples are the pact with the human; the harness
> keeps both honest.**

- **Naur, *Programming as Theory Building*.** A program is the theory its programmers hold. An agent
  loses the theory at the end of every session; the most faithful carrier of it is readable code,
  tests that tell the behavior, and a short living description — not a plan written before the
  code (mismAgent 0.2x wrote 55,000 words of it for 3,600 lines of code).
- **XP (Beck).** Simple design, test first, refactoring always, small releases, a coding standard,
  a second pair of eyes. Design emerges and is continuously improved; for an agent, refactoring is
  cheap and prediction is expensive.
- **Specification by Example (Adzic), Example Mapping (Wynne).** The human agrees concrete examples;
  they become executable acceptance tests.
- **Event Storming (Brandolini), strategic DDD (Evans).** The domain as a timeline of events, a
  shared language, contexts drawn where words change meaning. Tactical DDD is craft applied inside
  a slice when the code asks for it, never planned upfront.
- **Parnas** (modules hide decisions that may change) and **Feathers** (seams, characterization tests
  before changing code without tests).
- **Gause & Weinberg, the Socratic method.** Investigate, don't transcribe; confront options before
  deciding.

### The lineage: BMad and Agentheim
mismAgent is their heir and goes back to what they do best.
- **From Agentheim:** brainstorm → vision, context map and a walking-skeleton spike; the ubiquitous
  language per context; the board — folder = state, a read-only view of disk; the chronological
  diary; knowledge handed to the worker before it starts; a worker in red-green-refactor and a
  fresh-context verifier before the commit; research checked before it is cited; `inquire` and
  `whats-next`.
- **From BMad:** the delivery loop *Clarify → Plan → Build and verify → Learn and adjust*; a
  right-sized process (a clear change goes straight to build); specialized perspectives (analyst,
  product, UX, architect, developer, tester); advanced elicitation and party mode; a minimal project
  context, because "agents read code better than prose about code, and the copy goes stale"; in an
  existing codebase, build "looks at the code first, and stops to ask"; the retrospective.
- **What we leave:** the tactical backlog modeled before code, parallel execution by default, and
  the long document chain as the carrier of intent.

## 3. The four loops

```
 INTENT (with the human) — Clarify / Plan
   intake → explore (challenged) → investigate the domain and the UI → examples → slices
   ✋ the human approves the examples, the release cut, the stack
   │
   ├─ SLICE (one builder, one fresh session, in sequence) — Build and verify
   │    walking skeleton first, then one vertical slice at a time, end to end
   │    ├─ CRAFT (inside the session): acceptance test red → TDD → green → refactor → commit
   │    done = its examples green + all earlier ones green + a fresh reviewer's PASS
   │
   ├─ DESIGN (when the signals say so) — Learn and adjust
   │    a fresh architect reads the CODE → the design description → refactoring slices
   │
   ✋ release: the human sees the app running and accepts
```

**Intent.** Every request — a new product, a change, a second feature — enters through a short
**intake** that reads the request and the repository and proposes how deep the work needs to go.
The investigation is the stance of a detective and a senior process engineer: it looks for what is
missing, what contradicts, what nobody said; it argues the devil's advocate; it asks specific
questions, never generic ones. It builds the event timeline, asks of every event whether it can be
undone and what remains of it, maps rules to examples and questions, probes the edges, restates
each rule for the human to confirm. For a product with a user interface it investigates the user —
who, where, under which pressure — and proposes cheap mockups the human reacts to. It works **in
waves**: the whole product at the level of events, the detail only for the next release.

**Slice.** A slice is one path through the event timeline, from the action to what the user sees,
end to end. A builder, fresh, reads the design description, the language, the diary and its slice,
then the code; writes the acceptance tests first; works test-first; refactors; commits at every
green. A fresh reviewer checks that the tests really prove the examples and that the code meets the
standard. A slice lands only after the reviewer's PASS.

**Craft.** XP's inner loop, with its references (TDD, refactoring, simple design, clean code, SOLID,
frugality, tactical DDD) read when the code asks for them.

**Design.** When the signals say the structure is slipping, a fresh architect reads the code — not
the plan — rewrites the design description so it tells the truth, and queues refactoring slices
that preserve behavior. This is where the theory is curated: Agentheim's verifier and BMad's
retrospective, turned on the design.

## 4. Coherence from architecture to code

One line of decisions, each level written once and read by the next:
- **intent** — the problem, the language, the events, the examples;
- **architecture** — the choices expensive to reverse (language, interface toolkit, persistence,
  deployment), decided with the human, recorded as decisions;
- **design** — the modules and what each hides, the dependency directions, where the rules live, the
  conventions, the interface guide: one short description, rewritten from the code;
- **code** — every slice, read by every later slice.

**Style is a decision, not an accident.** The first time the code meets a new kind of thing (a
screen, a query, an error, a test) it sets the pattern the rest copies; a convention changes only by
an explicit decision, applied everywhere. A conflict between levels is a doubt, never a silent
divergence.

## 5. Code quality — a fixed point

Working software is not enough: the code must be clean, concise and well structured, to XP's
standard. Only clean code can carry the theory.

**The standard:** Beck's four rules of simple design (passes the tests · reveals intention · no
duplication · fewest elements); YAGNI; names from the domain; small cohesive units; modules that
hide one decision and depend in clear directions; no dead code; tests that are code too; the
stack's formatter and linter at zero warnings.

**How it is held:** sensors before judgement (what a tool can compute, a tool checks); refactoring
in every slice, not as an option; a reviewer who reviews on the same **review table** the code is
judged by, and blocks a slice for a quality defect in its own diff exactly as for a functional one;
structural debt paid while it is small. What decides whether this works is not a score but **the
cost and the defects of the next change**.

## 6. Doubts

A doubt is never guessed and never forwarded blindly. It is framed against what the files already
say; at a real fork the options are confronted Socratically — what does each assume, which example
does it break, what does it cost to reverse; the **important** ones (meaning, scope, money, the
stack, anything hard to reverse or outward-facing) go to the human with the options and a
recommendation; the local ones are decided and recorded.

## 7. Existing code

Before changing a codebase the harness has not built, it recovers its theory: the design as it is,
the behavior as it is, the language the code actually speaks. Code without tests gets
characterization tests before it is changed; touched code is left cleaner; the quality bar starts
where the code is and only rises.

## 8. The human

The human decides what "right" means and what is expensive to reverse: the challenger's verdict on
the idea, the examples and the release cut, the stack, the important doubts, each release. Nothing
else stops for them. What the human owns — the requirements, the examples, the acceptance tests —
the agents do not edit.

## 9. How the harness itself is kept

- **State in files and git**; any session resumes from disk; fresh sessions.
- **Evidence, never invention.** Every fact an agent states — a number, a limit, what a language,
  library, model or platform can do, a defect — carries its source (a file and line, a command run
  now, a page fetched, the human's words) or is written as an assumption with how to check it. The
  architect proves a capability (docs or a probe) before relying on it; decisions list their
  evidence. (The user's rule, 2026-09-29: the v0.2x flow invented context numbers.)
- **Tools compute, agents judge.**
- **Checker ≠ maker**, grounded in executable evidence.
- **In doubt, stop and ask**; a slow step is a strategy to replace, not something to wait out.
- **Sequential by default**; parallelism only when a measurement asks for it.
- **Every mechanism is a hypothesis** (layer 2): it enters the core only when an experiment
  confirms it, and leaves when an experiment shows it no longer earns its cost.
- **Budgets:** this vision ≤ 2,500 words; the core's prompts ≤ 5,000 words; its tool ≤ 500 lines;
  what an agent reads for one slice (the map, the skill's topics it touches, the tail of
  `progress.md`, the slice) ≤ 6,000 words for an app the size of the cash register — the history
  (reviews, done slices) is kept, never read whole, never compacted away.
- **Judged on the product, against the baseline:** acceptance, maintainability over a long horizon,
  exploration found, human attention, dollars.
